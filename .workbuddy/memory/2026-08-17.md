## 飞书多维表「记录链接生成器」自定义组件（新建项目）
- 目标：纯静态前端自定义组件，部署到静态站（GitHub Pages），在多维表「自定义组件 → 填网址」即用；为每行生成记录链接并写回对应行目标列。
- 技术栈：Vite + @lark-base-open/js-sdk（^1.0.2）；产物 dist/，vite base 设为 './' 以兼容 Pages 子路径。
- 关键 API：bitable.base.getActiveTable()；table.getFieldMetaList()；table.getRecordsByPage({pageSize}) 取 recordId；table.setCellValue(fieldId, recordId, value) 写回。
- appToken 取法：组件 iframe 的 document.referrer 里解析 /base/(...) 段，无需任何凭证；wiki 内嵌多维表 referrer 不含 appToken，UI 提供手动填写兜底（也支持裸 token）。
- 记录链接格式（**已修正**）：飞书「复制记录链接」的标准格式是 `https://<domain>/record/<recordId>`，仅依赖 recordId，不依赖 appToken/tableId。原 `?table=&record=` 格式在飞书前端解析不到具体记录、会跳回整个表格——这是用户反馈「转出来的是整个表格链接」的根因。务必用 `record/` 格式。
- 数据表选择：用 `bitable.base.getTableList(): Promise<ITable[]>` 列出所有表（含 id/name），`bitable.base.getTable(id)` 切换；默认选中 `getActiveTable()`。用户反馈「无法选择数据表」即因旧版只用了 getActiveTable 且无下拉。
- 数据表名称（**已修正**）：`getTableList()` 返回的 ITable 实例 `name` 经常为空，导致下拉显示成 tableId（用户反馈「数据表名称显示不对」）。改用 `getTableMetaList(): Promise<ITableMeta[]>` 拿名称最可靠（ITableMeta 明确带 name）；切换表时用 `getTable(id)` 取实例读写，并在 status 文案用 meta 的 name。
- 写入目标列（**已修正**）：飞书「链接/URL」字段的 setCellValue 不接受纯字符串，必须按 `{ text, link }` 结构写入，否则静默失败/被忽略（用户反馈「没写入相应地方」的根因，多为目标字段是链接类型）。修复：`generateLinks` 接收目标字段 `type`，链接类型写 `{ text, link }`、文本类型写字符串，两者互为兜底；`isUrlType` 兼容 type=15 或字符串 'url'/'link'/'hyperlink'。
- 记录读取健壮性（**Bug3 已修正**）：在飞书自定义组件(widget)环境下，`table.getRecordIdList()` **会返回空数组**，导致「点击开始生成立马显示完成但 0 条写入」。必须**优先用 `table.getRecordsByPage({pageSize, pageToken})`**（实测能正确返回 recordId 与 fields），`getRecordIdList` 仅作兜底。record 结构兼容 `recordId` / `id`。
- 诊断日志：点击「开始生成」后日志首行输出「已读取 N 条记录」，便于用户立即判断是“读不到记录(N=0)”还是“写入失败(N>0)”。
- 部署方式：改用「分支 gh-pages」托管 Pages（仓库原本即用此方式）；不再保留 GitHub Actions workflow。构建后把 dist/ 推到 gh-pages 分支即可，用户把 Pages 地址填进自定义组件 URL 即用。
- 限制/约定：按行串行写入避免飞书并发限流；处理当前数据表全部行（未做当前视图过滤）；**目标字段必须用「超链接」类型**，记录链接才会显示为可点击链接（用户明确要求，文本字段写入虽不报错但只是纯文本不可点击）。写入对超链接字段做多格式兜底（{text,link} → 字符串 → 数组），确保写入成功。

## Bug3 修复（已部署）
- 现象：点击「开始生成」立马显示完成，但超链接字段和文本字段都没写入。
- 根因：`getAllRecords` 当时优先 `getRecordIdList()`，而该 API 在 widget 环境返回空 → 读出 0 条 → 瞬间“完成”。
- 修复：改回**优先 `getRecordsByPage`**；超链接字段多格式兜底写入；加「已读取 N 条记录」诊断日志。main 提交 c773856；gh-pages 部署 b51a62c；线上 bundle index-DR2Cv_4m.js 已验证含修复标记。

## Bug4 修复（UI 报“写入完成”但目标列无链接）
- 现象：点「开始生成」很快报生成/写入完成，但选定的「超链接」字段列根本不出现记录链接。
- 根因（查 SDK 类型定义确认）：飞书「超链接/URL」字段取值类型 `IUrlField = IField<UrlTransformVal, IOpenUrlSegment$1[], IOpenUrlSegment$1[]>`（index.d.ts 1488 行），即**数组 `[{type:'url', text, link}]`**；`UrlTransformVal` 也允许**纯字符串**（1487 行）。而 `IOpenLink`（85 行）是「关联」字段格式，跟超链接无关。旧代码最优先写 `{text, link}`（文本字段行内链接结构），对超链接字段是不合法取值 → `setCellValue` 静默“成功”却存成空值 → 假成功。
- 修复：写入按字段类型选格式——超链接字段优先**纯字符串** `link`，其次 `[{type:'url',text,link}]`；文本字段优先 `{text,link}`。并新增**写后回读校验**：`setCellValue` 后立刻 `getCellValue` 读回，确认取值含链接才标记成功；回读不可用则信任写入；所有格式回读都空则告警。新增 `readCell`/`valueContainsLink` 辅助，第一格验证通过的格式会被 `verifiedFormat` 缓存复用，避免每行重复重试。
- 部署：main 提交 ae8ab8f；gh-pages 部署 ea4299e；线上 bundle index-CeWwWQrH.js 已验证含 `type:'url'`、`s.link`(回读)、`回读校验` 标记。GitHub Pages 有 CDN 缓存延迟（约 20s）才换新 bundle。

## Bug5 修复（生成的记录链接打开显示“页面不存在”）
- 现象：列里已能出现链接（Bug4 已修），但点开提示“页面不存在”。对比：生成的是 `https://my.feishu.cn/record/recvswCjq3nmi4`（13 位短 id），手动分享的是 `https://my.feishu.cn/record/PXsGrZ5xye0pZycaHY6cCYMznbf`（24 位规范 id）。
- 根因：`table.getRecordsByPage` 返回的 `recordId`（见 IRecord.recordId:739-740）是**客户端临时 id**——只对 `setCellValue` 有效（所以能写进正确行），但直接拼 `/record/<短id>` 不是公开可访问的规范链接，会跳“页面不存在”。手动“复制记录链接”用的是 24 位规范 recordId。
- 修复：改为调用 SDK 官方的 `table.getRecordShareLink(recordId): Promise<string>`（index.d.ts 1817-1821，注释“获取记录分享链接”）获取标准分享链接，返回即含 24 位规范 id 的 `https://<domain>/record/<id>`；仅在该方法不可用/失败时回退到 `buildRecordLink`（自行拼 domain）。新增 `getRecordLink()` 辅助，并首次生成时打印“示例记录链接：…”便于立即核对格式。
- 部署：main 提交 14909d9；gh-pages 部署 c3bd800；线上 bundle index-BsR7nDmw.js 已验证含 `getRecordShareLink`、`示例记录链接` 标记。

## Feat：提速 + 蓝链标准结构 + UI 美化（用户三点反馈）
- 背景：用户反馈（1）写入速度慢；（2）UI 不美观；（3）写入的链接是灰色不可点击，而蓝色才是真正可点击的超链接。
- 蓝链修复（根因）：上一版对超链接字段优先写了**裸字符串**，飞书将其渲染为灰色纯文本（不可点击）。正确做法是写标准结构 **`[{type:'url', text, link}]`**（对应 `IOpenSegmentType.Url='url'`，index.d.ts 26-30 行）。链接文本与 link 均取 `getRecordShareLink` 返回的完整 URL。
- 提速：① 用 `table.setRecords(records)` 批量写入（单次上限 200，按 100 分批），把“每行 1 次 setCellValue + 1 次回读”的 2N 次调用压成约 N/100 次；② 获取分享链接用 `mapWithConcurrency(records, 6, worker)` 限并发 6 调用 `getRecordShareLink`，避免限流；③ 写后回读校验只保留**首条一次**（不再是逐行回读）。批量失败自动退化为逐行写入并逐行定位失败。
- UI 美化：重做 `src/style.css`（飞书蓝渐变头部、卡片阴影、聚焦光环、渐变主按钮、彩色边框日志、圆角进度条）；`main.js` 的 `renderShell` 改为带品牌区（SVG 图标）+ body + footer 的卡片结构；首屏即展示飞书蓝主题。
- 部署：main 提交 0e5b62b（已推 origin）；gh-pages 部署 25175fa；线上 bundle index-zAtM8ZRn.js 已验证含 `type:"url"`(蓝链结构)、`setRecords`(批量提速)、`getRecordShareLink`(规范链接) 标记。
